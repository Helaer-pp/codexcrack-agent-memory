# CrackV4 下一轮优化与可视化验收任务书（四组试验均有逐帧双基准点）

> **直接交给代码 Agent 执行的 Prompt。** 你是一名熟悉 C++17、OpenCV 4.4、工业机器视觉、时序裂纹跟踪、几何配准、实验设计与性能工程的高级研发工程师。请基于已交付的 **NextRound OpenCV440 r1** 项目继续**实际修改代码、编译、完整回放四组真实数据、测量性能、生成视频和可追溯精度报告**。不得仅输出概念方案。

> **本轮关键变化**：现在四组试验**都有每一帧的两个基准点位置**，可作为已知逐帧几何输入，用于对照原自动配准。每组基准点必须来自该组自己的真实记录，不允许跨组复制。仍未说明是否存在真实裂纹尖端/中心线的人工标注；**基准点真值绝不等于裂纹尖端真值**，不能混淆。

## 0. 不可违反的边界

1. 保留现有传统视觉路线（参考帧 + 局部响应/黑帽 + DP 中心线 + Tile 跟踪 + root/terminal/temporal）；**不引入神经网络、训练模型或在线推理**。
2. 只优化和评价**像素坐标、像素长度、有效性状态**。毫米/物理长度换算不在本轮范围内；如旧 ABI 需要毫米字段，保持兼容但不作为新版本验收指标。
3. 目标 **≥15 Hz**，算法单帧预算 **66.67 ms**。此次**不计照片读取、解码、磁盘 I/O、视频编码、绘图、UI 和相机等待**；需要分开计量。算法统计必须覆盖内存 `CV_8UC1` 输入的实际检测调用及必要的生产级配准/审计逻辑，所有正常、错误和回退帧均计入。
4. 四组已有试验的已知正常结果不得无依据退化；**不允许靠大量输出 uncertain/invalid 冒充精度提升**。新策略必须可关闭、可回退，并与冻结版本逐帧对比。
5. **不实施任何静默伪造**：不生成假基准点、不以旧算法结果冒充人工真值、不把缺少真值的代理差异命名为“实际精度”、不以视频看起来平滑代替数值验收。
6. 如果四组图像、逐帧基准点文件、最新源码/构建环境尚未提供，先检查并明确缺失项。可以准备代码/测试框架，但不能宣称已完成四组数值验证或已生成实际效果视频。

## 2. 固定基线和对照组：必须至少跑以下配置

对每组**每次使用独立 Detector 实例**，从参考帧初始化，按真实帧顺序连续回放，保留历史状态，绝不可在一个实例中混用不同策略导致历史污染。

| 配置 ID | 基准点输入 | 版本/审计策略 | 目的 |
|---|---|---|---|
| `AUTO_BASE` | 当前点为 NULL | 冻结旧版或可复现的对应默认基线 | 自动配准旧行为 |
| `AUTO_NEW_SHADOW` | 当前点为 NULL | 最新版 `flags=244` / Shadow | 复现最新报告 |
| `ANCHOR_NEW_SHADOW` | 四组真实逐帧 P1/P2 | 最新版 `flags=244` / Shadow | **本轮最重要的对照** |
| `ANCHOR_NEW_VERIFIED` | 四组真实逐帧 P1/P2 | 最新版 Verified（实验） | 观察真正闭环覆盖率与误拒绝 |
| `ANCHOR_OPT` | 四组真实逐帧 P1/P2 | 本轮经过验证的改进方案 | 优化后正式候选 |

若接口不支持某种组合，先明确实际支持关系；不得伪称运行成功。可选补充 `AUTO_OPT`，用于检查优化是否会损害缺少外部点时的自动模式。

**注意**：`flags=244` 由多个实验标志组合，属于报告所述的实验修正集合，并不等同于“启用 Verified”。必须分别记录 `Shadow` 与 `Verified` 的真实生效设置和运行路径。默认兼容接口仍应保持原行为，只有完成验收后才考虑更改默认配置。

## 3. 首要任务：借助四组真实双点，查清配准失败与“成功但误配”

### 3.1 用四组双点建立配准误差的独立衡量

对于每一帧，从自动配准结果 `T_auto` 计算参考点预测位置：

```text
q1_auto = T_auto(p1_reference)
q2_auto = T_auto(p2_reference)
e1 = ||q1_auto - p1_measured_current||
e2 = ||q2_auto - p2_measured_current||
```

同时输出 `max(e1,e2)`、两点平均误差、角度差、两点间距变化、旋转和平移跳变；异常点必须结合外部基准点自身质量审查。统计 P50、P90、P95、P99、Max，以及大误差帧清单（门限应依据有标注/工程需求或分布实测设定，不要凭空声明通用阈值）。**这直接评估几何配准的点位残差，不等于裂纹尖端误差**。

### 3.2 重点复现已有失败

- 原 CT2 **27 帧**、开发组H MT **5 帧**自动配准失败：用真实 P1/P2 对照最新有界恢复后的变换是否正确；分析恢复后 CT2 27 帧及开发组H 3 帧新增已确认尖端的局部图像证据。
- 报告中的合成 `(7,-31)` 自动配准**成功但误配**，尖端误差约 **360.02 px**：恢复并测试；当提供真实当前双点时，此合成场景尖端误差曾约 **2.61 px**。本轮要求自动模式在此反例**不再无证据地输出错误确认**。
- 比较四组真实数据中：`AUTO_NEW_SHADOW` vs `ANCHOR_NEW_SHADOW` 的配准残差、错误数、帧间稳定性、尖端/路径变化及 stop reason。所有大差异必须输出可视化证据。

### 3.3 仅在证据指向问题时实施轻量改进

优先检测**配准返回成功但质量不可靠**的情况，候选措施包括：多 ROI 独立复核、相位峰值歧义检查、空间残差一致性、外部双点几何约束、与相邻帧的合理运动一致性。可靠真实双点输入时优先使用双点刚体配准，并审查现有 patch refine 是否造成错误反向修正；不可将“patch 很少”直接判为配准错误。

分别明确 `REGISTRATION_VALID / REGISTRATION_AMBIGUOUS / REGISTRATION_FAILED` 语义，并严格区分 `current_anchor_valid`。自动/外部双点存在分歧时，不得简单无条件相信任意一方；没有足够证据时将当前测量标为不确定，历史结果独立保存，不伪造本帧确认。

如果正常帧已有可靠双点且结果正确，**不要为了“提高普适性”而无条件引入 ECC、全图匹配或任意仿射变形**。

## 4. 第二任务：用真实双点隔离裂纹检测自身的误差

四组全部使用同一组数据集各自的真实逐帧双点后，检查以下因素：

1. **错误分解**：由自动配准切到真实双点后，哪些帧的路径/尖端恢复稳定？哪些仍然存在路径漂移、低响应、假尖端或明显错误？将“几何问题”和“路径/终端证据问题”分开分类。
2. **方向约定**：保留已验证的方向修正（开发组H both 阴影从 825.25→3.29 px、2004.93→0.48 px 的代理稳定性改善），但把 `AnchorPositive / AnchorNegative / Auto` 或等价显式方向设置做成可选配置。不得静默假设所有试件都是“p1在上、p2在下且向右扩展”；对当前四组使用有图像证据的方向定义。
3. **CT2 过曝**：已有第 24 帧 +25 灰度饱和导致约 278.04 px 代理偏差；区分可校正增益变化和不可逆细节丢失。必要时增加局部饱和/纹理失效的轻量审计，不能宣称从已饱和图像恢复不可见真实尖端。
4. **终端证据**：继续拆分 `tracking_endpoint`、`tip_confirmed`、`root_confirmed`、`complete_length_valid`。解决“局部跟踪结束但物理裂纹并未结束”的假尖端；保留可见路径供诊断，不强行回填历史坐标。
5. **Verified 大量拒绝**：报告中旧接受/Shadow 拒绝为 417 帧，反向分歧 20 项；最新闭环 `Verified` 相比 Shadow 仍大幅降低确认覆盖，尤其 CT2。四组真实双点可将“配准不确定”影响从路径与尖端审计中分离。按 `registration_uncertain / possible_forward_continuation / endpoint_temporal_pending / weak_terminal` 等原因逐项统计与复核。不能一刀切降低阈值。
6. **遮挡与闭合**：保留已知合成遮挡审计，允许裂纹可见长度因闭合或姿态改变而回落，**不得强加单调长度先验**。局部近常值区域不可见，不得当成已经找到物理尖端。

要求：一项根因、一项可回退修复、一项对照实验。优先在已有 `tile` / 末端 ROI / 时序结构上实现低成本验证。不要进行整幅图像多尺度重算或改变稳定的 DP 数值顺序，除非数据证明必须改变。

## 5. 真值与精度评估：必须严谨，不得拿基准点当裂纹标注

### 5.1 四组逐帧基准点真值能直接验证的指标

- 自动配准对真实 P1/P2 的逐帧误差（上述 `e1,e2`）、角度与几何残差；
- 外部双点的完整率、异常率、异常帧列表（输入数据质量，不是模型预测准确率）；
- 同一帧自动 vs 真实双点的裂纹路径/尖端差异、确认状态翻转、长度差；
- 时序平滑性/异常跳变（只称稳定性或一致性指标，**不是**实际尖端精度）；
- 配准失败、恢复、错误确认、不确定、覆盖率和确认延迟。

### 5.2 裂纹尖端/像素长度真实精度必须依赖独立标注

先检索是否已有**人工标注的真实裂纹尖端、根部、中心线路径**。如果有，按数据集输出：尖端欧氏误差 Px 的 MAE/P50/P95/Max、完整长度绝对误差和有符号偏差、检出率、误报率、确认覆盖率及不确定比例。误报/漏报必须以真实裂纹是否存在为依据，不能直接从 `tip_confirmed` 数量推断。

如果没有，**必须**：

1. 生成供人工复核的样例包及标注模板：优先包括原 32 帧恢复、4 组较大几何残差、Shadow/Verified 分歧、CT2 过曝、开发组H阴影、合成遮挡；每组补充早/中/晚及较短、较长、低对比度帧。
2. 提供 CSV/JSON 标注 schema：`dataset,frame_id,crack_visible,tip_visible,tip_x,tip_y,root_visible,root_x,root_y,length_px_gt,annotator,review_status,notes`；有些项目只有尖端标注，无真实完整弧长时长度真值留空，绝不能用检测器路径代替。
3. 若可进行可靠人工标注，可生成**明确标为人工标注**的验证子集并接受抽查；不能把自动路径直接回写成 GT。若没有人工参与或标注能力，输出 `tip_ground_truth_available=false`，实际尖端/长度精度列填写 `N/A（缺少独立真值）`，同时提供可复查的代理指标。
4. 保留已知真值的合成场景作为另一个独立评价区，注明其数据分布与真实试验不同；不能把合成 P95 直接称为四组真实数据精度。

### 5.3 禁止的虚假验收表述

- “四组均有基准点，所以四组裂纹尖端精度已知”：**错误**。
- “与冻结版逐帧零差异，所以精度 100%”：**错误**。
- “确认帧更多，所以误检率下降”：**不成立**。
- “没有超过 66.67 ms，所以包含视频生成仍有 15 Hz”：**不成立**（视频编码与绘制未计）。

## 6. 性能要求（只评价检测计算）

运行环境优先沿用报告：Ryzen 9 7950X、Windows x64、Release /O2 /fp:precise、OpenCV 4.4、四线程。若实际环境不同，先建立完整同机基线，不直接比较绝对数字。

上一轮实验模式原生处理耗时参考：

| 组别 | P95 ms | P99 ms | 最大 ms |
|---|---:|---:|---:|
| 开发组A | 10.19 | 11.70 | 13.26 |
| 验证组C | 5.67 | 6.13 | 6.80 |
| CT2 | 21.80 | 24.21 | 28.86 |
| 开发组H MT | 40.70 | 45.48 | 52.85 |

- 四组全部图像**先读取、解码并驻留内存**，预热后按完整帧顺序运行；分别测量上述配置，必须保持各配置自己的时序历史。记录 P50/P95/P99/Max、超 66.67 ms 帧数、错误帧与 fallback 帧耗时、实际线程数、峰值内存和图像尺寸。
- 计时包含 `Process` 的配准、seed、tile、DP、末端/时序审计及结果填充。**如果实际生产中逐帧需要运行双点有效性检查，也应计入**；单纯读取 CSV 可以单独列出、不混淆“算法耗时”。
- 与检测分开统计 `LastJson`、`CopyPath`、可视化叠加和 MP4 编码耗时。绝不把图像/视频渲染计入检测内核，也不把它们的耗时删除后宣称整个应用实时。
- 主要硬门槛：在相同的目标验证机器、相同配置下，所有测试帧（包括异常/回退）单次算法处理尽量满足 **≤66.67ms**；如存在超预算帧，必须报告并明确表示 15 Hz 目标未通过。开发组H设计参考仍为 P95≤55ms、P99≤60ms，不能因切换真实双点而假设自动达标。
- 如果提高精度的候选方案使 P99 明显恶化，应提供准确性收益与性能代价的配对证据；没有独立准确性证据的重型模块不得启用。

## 7. 必须真实生成优化后裂纹计算效果视频（MP4）

**最终交付要求，不是可选建议。** 在实际四组数据齐备且能运行工程时，至少输出每组 **1 个完整序列的 MP4**，另输出每组代表性前/中/后段的预览短视频；有条件再输出优化前后并排对比视频。

每帧叠加应包括：

- 数据组名称、源 `frame_id`、输入分辨率、视频中的顺序编号；
- 参考/当前 P1、P2（不同形状/颜色，不应将参考点未配准坐标直接绘到当前图上）；
- 检测中心线及其末端；明确区分 **当前跟踪终点（候选）** 与 **已确认真实裂纹尖端**；
- 根部、`tracked_length_px`、`complete_length_px`（无效时显示 `N/A`）、`tip_confirmed / root_confirmed / complete_length_valid`；
- `registration_state`、配准误差 `e1/e2`（适用于当前配置）、置信/审计原因、`stop_reason`；
- 若已存在独立尖端真值，叠加 GT 与误差；否则画面不得显示“GT tip error=0”之类的虚构数字。

**视频格式与验证**：

- 建议路径：`deliverables/videos/{dataset}_anchor_optimized.mp4` 和 `deliverables/videos/{dataset}_before_after.mp4`；采用常见 H.264（优先）或兼容的 MP4 编码，保留原帧宽高比例，若因超高分辨率缩放则同步变换所有坐标和绘制尺寸。
- 以真实源 FPS 生成；如果原始序列无 FPS 信息，明确使用演示 FPS（建议 15 FPS），并声明 **视频播放 FPS 不等于算法达到 15 Hz**。
