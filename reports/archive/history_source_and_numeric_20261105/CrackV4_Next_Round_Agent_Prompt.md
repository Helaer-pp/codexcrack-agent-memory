## 2. 业务范围与硬约束

### 2.1 功能目标

- 已知参考图、参考定位点、连续图像序列；主要目标仍是**单条主裂纹的识别、中心线跟踪、尖端识别和长度测量**，不是任意图像全图多裂纹通用分割。
- 核心输出是：**尖端像素坐标、根部像素坐标、跟踪终点像素坐标、可见/跟踪路径像素弧长、根部至尖端像素弧长**，以及有效性与不确定状态。若尖端或根部未确认，不能将候选结果冒充已确认结果。
- `mm_per_pixel`、毫米长度及物理标定**不属于本轮优化范围**。如为 ABI 兼容保留旧字段，不能把毫米换算当作本轮性能与精度指标。
- 禁止引入 CNN、Transformer、ONNX 推理、神经网络模型或需要训练的识别器。保留 C++17 + OpenCV 的传统视觉路线。
- 已有四组真实试验在旧默认策略下通过验证。**不得以大范围改阈值、默认启用 Verified、降低确认覆盖率等方式，未经真值验证便宣称更准确。**

### 2.2 速度约束：本轮不考核照片读取耗时

- 目标处理频率 **≥15 Hz**，即单帧算法调用的 **66.67 ms** 时间预算（目标硬件/相同编译配置）。
- **不计入**：`imread`、磁盘 I/O、JPEG/PNG 解码、离线文件扫描、写入报告/图片、绘制可视化、UI 显示和相机采集等待。
- **计入**：已在内存的 `CV_8UC1` 图像进入生产检测调用后，配准、seed、tile、DP、末端审计、时序更新、结果结构填充等实际计算。若生产路径要求 `CopyPath`/`LastJson`，另外报告这些调用的开销；不能只测核心后声称包括所有附加接口。
- 使用**驻留内存图像**做主速度基准；离线读图时间不得作为本轮失败理由，也不得被算作算法性能改善。
- 在相同 CPU、OpenCV、Release 编译、线程数、测试样本、缓存和负载条件下，比较原优化版与候选版本；至少给出 P50、P95、P99、Max、超过 66.67ms 的帧数，**错误帧与触发 fallback 的帧单独统计并纳入最坏延迟审查**。
- 以前一轮同机四线程 Release 为参考，开发组H MT 的 C API P95 = **50.86ms**、P99 = **54.77ms**、有效帧最大 **57.35ms**，是当前最需要保护的性能预算。工程目标：正常/回退场景都尽量不超过 66.67ms；优先争取开发组H P95 ≤55ms、P99 ≤60ms。后两个数是**暂定设计目标**，不是旧项目已实现的保证；若硬件或测试环境不同，先重新建可比基线。
- 不要在没有 profiling 证明瓶颈时开发全量 FastTrack、每帧全图多尺度、ECC/仿射配准或大范围搜索。

## 5. 测试策略与质量门槛

### 5.1 分清三类测试，不能互相替代

**A. 四组真实原始序列回归**

- 每组以真实参考图初始化一次，再按真实顺序处理全部当前帧，保留完整 detector 状态；不要把独立抽帧重建状态当作完整时序回归。
- 与上轮正式默认结果逐帧比较：状态、`tip_confirmed`、root、尖端/追踪终点像素坐标、可见/完整像素弧长、中心线路径、history 与 stop reason。
- 默认策略的任何变化都逐项列出；**没有真值的变化标记为“未判定好坏”**。不得靠大量新增 uncertain 使误报率看起来降低。
- 对 Shadow/Verified 输出分开统计，且区分旁路判定和实际启用 Verified 后的闭环结果。

**B. 已知真值的合成场景**

- 保留报告的 `strong / weak / clean / translation / rotation / opening / boundary / precracked / missing_evidence / occluded_tail` 10 类场景。
- 增加：局部阴影覆盖入口、阴影覆盖中部或尾部、曝光跳变、短暂遮挡后恢复、真实尖端高速增长、重复帧/跳帧、配准纹理弱/局部失败。
- 明确模拟物理裂纹真值、可见裂纹终点和参考坐标/当前坐标的差别；精度指标以真值计算，路径偏差单独计算。

**C. 受控真实图扰动（代理稳定性）**

- 复现报告种子 `20261028` 的 240 个案例，覆盖加亮、gamma、对比度、局部阴影、噪声、失焦、平移、旋转、anchor 抖动、尺度变化，以及 `reference+current` 同变与 `current-only` 两类。
- 重点关注开发组H阴影 **2004.93/825.25px** 与 CT2 曝光 **278.04px** 的案例；对于只改变光照的扰动，应核对是否出现异常方向切换、路径分叉或确认丢失。
- 报告“代理偏差”的前提和不可替代真值的局限；对失去确认的帧另列，不把其偏差算作 0。

### 5.2 最少应报告的指标

- 有人工/合成真值时：尖端坐标误差（px，P50/P95/Max）、长度有符号/绝对误差（px）、漏检/误检、首次确认帧、错误尖端率。
- 无人工真值时：原版/新版逐帧差异、确认覆盖率、pending/uncertain/error、分歧原因分布、扰动前后坐标代理偏差、路径漂移、图像质量门控触发率。
- 性能：完整内存驻留图像序列的生产 C API 每帧耗时 P50/P95/P99/Max、超 66.67ms 帧数、正常/异常/fallback 的分布、各阶段 profiling。**不算读图/解码**。
- 稳定性：批量长循环内存增长、多实例隔离、ResetTemporal、reference query 纯读、C ABI 与旧 SDK 兼容；不得回退上一轮 15/15 工程测试。

### 5.3 通过/回退原则

1. **正确性优先**：禁止人为编造真值、跳过错误帧、删除困难帧、隐瞒失效例。
2. **原有四组正常输出不轻易退化**：默认行为变化须有逐帧列举与可解释、可复查证据；对无法判断的变化保留实验开关，暂不默认启用。
3. **优先解决已知灾难案例**：明确展示失败原因消除和跨场景未受损，而不是单纯把输出从“确认”改成“未确认”或裁剪坐标。
4. **速度**：目标硬件上至少 15 Hz 的算法计算预算；正常帧、错误帧、fallback 帧都记录。若某方案降低精度或突破 66.67ms，关闭该方案、保留诊断结论。
5. **新增标注不足**：保持 Verified 为实验模式，提交标注包与风险报告，不能宣称已经达到未知场景的普适性保证。

## 6. 执行过程要求

1. **基线复核**：先输出实际代码版本、已有功能清单、可用四组数据、报告复现情况、旧版本计时及已知失败是否复现。
2. **诊断先行**：优先交付开发组H/CT2 分歧根因、32 错误帧的分类、Shadow 417 拒绝的分布，并指出缺失的人工真值。
3. **修改规模受控**：一个逻辑问题一个小变更；记录文件、函数、行为开关、预期影响、性能代价及回退方法。不要同时修改配准、黑帽、DP、时序和 API 导致无法归因。
4. **先做实验开关**：对于改变确认结果/路径的逻辑，先 Shadow 或 opt-in，实现旁路对照与闭环回归；未经证据通过不得默认切换。
5. **每个变更后编译与测试**：保留原版/当前优化版可回放的 DLL 或构建产物；完整记录失败与差异，出现回归时先回退再分析。
6. **对关键问题优先制作可复查图**：原图、扰动图、局部 ROI、旧/新路径、真实/代理坐标、发生分叉的首个 tile、响应或掩膜叠加。
7. **可维护性**：保持 C++17、OpenCV、已有 C ABI、Pixel V2 接口和数值兼容行为；新增日志只在开启诊断时产生，避免污染正式耗时。
8. **在无法继续时明确阻碍**：缺源码、缺四组图片、缺上一轮脚本或缺标注时，列出所需文件与可以完成的部分。不要以没有测试数据为由声称修复已验证。
